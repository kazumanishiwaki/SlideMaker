この文書は、現行実装が満たしている要件と、次に実装する要件を分けて整理する。

事業責任者、正式なサービスレベル、運用体制、外部公開方針はリポジトリだけでは確定できないため、未確定事項として分離する。

## 背景と課題

PowerPoint資料の生成では、原稿の事実を守ること、任意テンプレートの見た目を引き継ぐこと、生成後も編集できることを同時に満たす必要がある。

テンプレートのブランド要素がマスターやレイアウトに収まらず、完成済みスライドへ直接配置されている場合もある。

そのため、単純な新規描画だけではテンプレートの再現性が不足し、完成済みスライドの単純な複製だけでは原稿に合う構成と編集性を保ちにくい。

SlideHarnessは、原稿の根拠、テンプレートの設計証拠、編集可能なPowerPoint要素、実レンダーに基づく品質検査を一つの生成工程として扱う。

## 目的

- 任意の原稿とPowerPointテンプレートから、編集可能なPPTXを生成する。
- 原稿中の必須情報、数値、日付、条件と出典の対応を保持する。
- テンプレートがマスター中心か完成スライド中心かに応じて合成方法を変える。
- 自動検査で内容、構造、PPTXパッケージ、出典、レンダー結果を確認する。
- 1ページ修正時に指定外ページが変わっていないことを機械的に証明する。
- スキャンPDFを原稿として扱えるようにする。
- データに適した複数種類の編集可能なPowerPointグラフを生成する。
- 画像要求の生成から画像登録、PPTX生成再開までを自動化する。
- 品質を維持できる処理では生成AIを呼ばず、処理時間とトークン消費を削減する。
- AI経路と非AI経路に同じ構成契約とQAを適用し、出力を標準化する。

## 実装範囲

現行コードは次の対象を実装する。

1. スキャンPDFのOCR。
2. 棒グラフ以外のPowerPointネイティブグラフ。
3. 画像生成の自動実行。
4. 上記を支える決定論的処理、キャッシュ、差分コンテキスト、共通出力プロファイル。

ラン管理、クラウド公開、外部認証など、これら以外の拡張は後回しとする。

## 利用者と役割

| 役割 | 主な責務 |
|---|---|
| 資料作成者 | テンプレート、原稿、任意のデザイン指示を登録し、生成方針を選ぶ |
| 資料レビュー担当者 | モンタージュ、PPTX、QAレポートを確認し、人による最終承認を行う |
| ローカル運用者 | Node.js、Python、LibreOffice、Poppler、Codex実行環境を準備する |
| サインイン済みCodex App Server | 根拠に基づくデッキ構成、指定された1ページの再構成案、必要な生成画像を作成する |

## 利用シナリオ

### UC-01 新規資料を生成する

1. 資料作成者が案件を作成する。
2. 資料作成者がテンプレートと1件以上の原稿を登録する。
3. 必要に応じてデザイン指示書と追加指示を登録する。
4. 資料作成者が合成モード、情報量、装飾性、グラフとフロー図の表現方式を選ぶ。
5. システムが原稿とテンプレートを解析し、テキスト抽出が不十分なPDFページだけをOCRする。
6. Codexが根拠に対応した構成を作成する。
7. システムがPPTXを生成してQAを実行する。
8. 画像が不足する場合、システムが要求IDに対応する画像を自動生成して登録する。
9. 自動生成に失敗した場合だけ、資料作成者が画像を手動登録する。
10. すべての必須QAに合格した場合、システムがPPTXとモンタージュを提示する。
11. 資料レビュー担当者が全ページを目視確認する。

### UC-02 1ページだけを修正する

1. 完成済み資料から対象ページを選ぶ。
2. 修正指示とページ別の情報量、装飾性、表現方式を指定する。
3. Codexが対象ページの構成オブジェクトだけを作成する。
4. システムが候補資料を生成してQAを実行する。
5. システムが対象ページとその専用依存物だけを現行PPTXへ移す。
6. 指定外ページのフィンガープリントがすべて一致した場合だけ改訂を確定する。
7. 失敗時は現行PPTXと現行プランを維持する。

## 機能要件

### 入力と設定

| ID | 要件 | 受入条件 | 対応機能 |
|---|---|---|---|
| FR-001 | システムはPPTXまたはPOTXのテンプレートを1件受け付ける | 0バイトを拒否し、上限50MBと拡張子を検証する | F-002 |
| FR-002 | システムは対応形式の原稿を1件以上受け付ける | Markdown、TXT、DOCX、PDF、PPTXを受け付け、各ファイルの上限を25MBとする | F-003 |
| FR-003 | システムはデザイン指示書を原稿とは別の入力として扱う | デザイン指示の文章が出典事実や必須情報として混入しない | F-004 |
| FR-004 | 利用者は合成モードを選択できる | `auto`、`reconstruct`、`source-slides`以外を拒否する | F-005 |
| FR-005 | 利用者は情報量と装飾性をそれぞれ3段階で選択できる | `low`、`medium`、`high`以外を拒否し、選択値をラン設定と構成メタデータへ保持する | F-006、F-007 |
| FR-006 | 利用者はグラフとフロー図の表現方式を選択できる | `auto`、`native`、`generated-image`以外を拒否する | F-008 |
| FR-007 | システムはドロップシャドウを初期状態で禁止する | 明示的な許可がない生成物に影が残る場合、構造QAを失敗させる | F-009 |

### 解析と構成

| ID | 要件 | 受入条件 | 対応機能 |
|---|---|---|---|
| FR-008 | システムは入力原稿を不変の出典単位へ分割する | 各単位に出典ファイル、順序、原文、正規化文、分類、事実、必須フラグを記録する | F-010 |
| FR-009 | システムは数値、日付、金額、割合、条件を必須確認対象として抽出する | 構成に採用された事実が原稿に存在し、必須事実の欠落をQAで検出できる | F-010、F-019 |
| FR-010 | システムはテンプレートのテーマと構成証拠を抽出する | 色、フォント、ページ寸法、レイアウト、反復要素、パターン証拠をJSONへ出力する | F-011 |
| FR-011 | `auto` 合成モードはテンプレートリスクに基づいて実方式を選ぶ | 完成スライド偏重かつリスクが高い場合は `source-slides`、それ以外は `reconstruct` を選ぶ | F-005、F-015 |
| FR-012 | Codexが作成する初期プランは `plan/deck_spec.json` の1ファイルに限定する | 入力と `prepared/` を変更せず、必須出典単位を採用し、許可済みレシピだけを使用する | F-012 |
| FR-013 | システムは構成内容を原稿と照合する | 未知の出典ID、必須単位欠落、必須事実欠落、未裏付け事実、重複スライドID、不正レシピを拒否する | F-019 |

### PowerPoint生成

| ID | 要件 | 受入条件 | 対応機能 |
|---|---|---|---|
| FR-014 | システムは構成から編集可能なPPTXを生成する | テキスト、図形、表、対応する構造図をPowerPointオブジェクトとして保持する | F-014、F-016 |
| FR-015 | `source-slides` は参照スライドのOOXMLと関連を複製して内容を置換する | レイアウト関係、ブランド要素、反復装飾を保持し、未使用のダミーテキストと空構造プレースホルダーを残さない | F-015 |
| FR-016 | ネイティブ表現では表、棒グラフ、フローを編集可能にする | 表はPowerPoint表、棒グラフはPowerPointグラフ、フローは個別図形と接続線で構成する | F-016 |
| FR-017 | 生成画像表現でも事実上の結論を編集可能なテキストへ残す | `generated_visual` のタイトルとメッセージに結論を保持し、画像要求に必要なラベル、値、関係、読み順を含める | F-017 |
| FR-018 | 解決済み画像は初期状態で1回だけ使用する | 同じ画像パスの重複利用を拒否し、個別要求の `allow_reuse: true` がある場合だけ許可する | F-017 |
| FR-019 | 外部画像の出典を記録する | 安定した `asset_id` と正確な `source_url` または `source_urls` を構成とノートへ保持する | F-018 |
| FR-020 | 生成テキストを自動縮小しない | 固定フォントサイズで生成し、欠落や折返しをQAで検出する | F-021 |

### QAと成果物

| ID | 要件 | 受入条件 | 対応機能 |
|---|---|---|---|
| FR-021 | システムは内容、構造、パッケージ、出典、レンダー、視覚のQAを実行する | 最終サマリーに各QAの結果を記録し、ブロッキング所見があれば完成扱いにしない | F-019、F-020、F-021 |
| FR-022 | 最終生成は実レンダーを必須とする | レンダー結果が `SKIP` の場合、明示的な草稿用例外がない限り失敗する | F-021 |
| FR-023 | 自動QAの合格と人による承認を区別する | 成功時もレビュー用パケットを作成し、承認状態を自動で承認済みにしない | F-021、F-022 |
| FR-024 | 成功時にPPTXとモンタージュを提供する | 出力ディレクトリ配下の成果物だけをHTTPで取得できる | F-022 |
| FR-025 | 原稿に基づくページへ出典ノートを付ける | ノートが `[Sources]` で始まり、使用した出典単位IDと必要なURLを含み、ローカル絶対パスを含まない | F-018 |

### 1ページ再生成

| ID | 要件 | 受入条件 | 対応機能 |
|---|---|---|---|
| FR-026 | 1ページ再生成は完成済み資料だけに許可する | 完成PPTXがないランと同時実行中の再生成要求を拒否する | F-023 |
| FR-027 | 再生成要求は安定した `slide_id` と期待リビジョンを持つ | 対象IDが存在しない場合と、期待リビジョンが現行値と異なる場合を拒否する | F-023 |
| FR-028 | Codexは対象ページの構成オブジェクトだけを作成する | `slide_id` を変更せず、対象外ページと現行プラン本体を直接変更しない | F-023 |
| FR-029 | システムは指定外ページの不変性を検証する | 対象外ページのスライドXML、関連、再帰依存関係のフィンガープリントがすべて一致する | F-024 |
| FR-030 | システムは共有依存物の変更を拒否する | 対象ページの変更が他ページと共有するテーマ、メディア、グラフなどへ及ぶ場合は適用しない | F-024 |
| FR-031 | 再生成失敗時は直前の有効成果物を維持する | 現行PPTX、現行プラン、リビジョンを変更せず、失敗理由を状態へ記録する | F-024、F-025 |
| FR-032 | 再生成成功前に旧版を保存する | `versions/rev-NNNN/` に直前のPPTX、構成、存在する場合はサマリーを保存する | F-025 |

以下の要件は現行コードの対象である。

| ID | 要件 | 受入条件 | 対応機能 |

| FR-036 | システムは複数種類の編集可能なPowerPointグラフを生成する | 棒、縦棒、積み上げ、折れ線、面、円、ドーナツ、散布図をPowerPointグラフとして生成できる | F-029 |
| FR-037 | システムはデータ特性からグラフ種類を決定論的に選択できる | 時系列、構成比、相関、カテゴリ比較を構造化データから判定し、判断できない場合だけCodexまたは利用者へ選択を委ねる | F-029、F-031 |
| FR-038 | ネイティブグラフは共通スタイルを使用する | テーマ色、フォント、軸、凡例、データラベル、数値書式、アクセシビリティ用説明を共通プロファイルから適用する | F-029、F-034 |
| FR-039 | 画像要求をCodex App Serverへ自動送信する | 未解決の `asset_id` ごとにサインイン済みCodex App Serverの組み込み画像生成を実行し、`item/completed` の `imageGeneration.savedPath` から画像を取得して、要求IDを維持したままアセットマニフェストへ登録し、同じランを再開する | F-030 |
| FR-040 | 自動画像生成の失敗から再生成または手動処理へ移行できる | 品質審査の具体的な修正指示で最大2案まで生成し、それでも不合格、利用上限、タイムアウト、生成失敗の場合は理由を記録して既存の画像アップロード待ちへ安全にフォールバックする | F-030 |

| FR-043 | 同じ入力と設定の処理結果を再利用する | 内容アドレスが一致するOCR、生成画像、最終QA合格済み構成プランを再利用し、再利用後も共通QAを省略しない | F-032 |

## 制約

- App Serverは単一ホスト上のローカル利用を前提とする。
- Codexによる構成、1ページ再生成、画像生成には、利用者がサインイン済みで画像生成能力を提供するCodex App Server実行環境が必要である。
- スキャンPDFのOCRにはTesseractとPopplerのページ画像化コマンドが必要である。
- 自動画像生成はCodex App Serverが公開する `modelProvider/capabilities/read` の `imageGeneration` 能力を使用する。能力がない場合、利用上限、タイムアウト、生成失敗、QA不合格の場合は手動アップロード待ちへ移る。
- 生成画像内の構造図は `required_text` を必須とし、OCRで確認できないラベルがある場合は完成扱いにしない。
- 本文中の「生成AI」はCodexによる構成と画像生成を指し、決定論的なローカルOCR、構文解析、数値処理、PPTX生成、QAとは区別する。
- `archive/v0.10/` は現行システムの依存先にしない。
